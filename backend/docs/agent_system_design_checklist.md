# 开发 Agent 时的大方向清单

这份文档不是针对某一个功能，而是为了提醒自己：做一个 Agent 系统时，有哪些重要方向必须提前想到。即使当前还不做，也要知道它们会影响系统设计。

## 1. 产品边界
先明确：
- 这个 Agent 是做什么的
- 不做什么
- 面向什么用户
- 核心任务是什么

如果边界不清，后面路由、工具、记忆、前端都会变形。

## 2. 状态设计
Agent 几乎一定会涉及状态。

常见状态包括：
- 会话状态
- 任务状态
- 业务对象状态
- 用户状态

如果一开始不想清楚，后面加多轮对话、编辑、恢复、记忆时会很痛苦。

## 3. 记忆系统
需要思考：
- 是否需要短期记忆
- 是否需要长期记忆
- 记住什么
- 什么时候写入记忆
- 什么时候读取记忆
- 记忆错误时如何修正

记忆会影响个性化、多轮连续性和系统复杂度。

## 4. 长上下文管理
大模型上下文有限，所以必须考虑：
- 长文本怎么切分
- 长对话怎么压缩
- 哪些历史必须保留
- 哪些历史可以摘要化
- 如何控制 token 成本

这是 Agent 和简单聊天应用的重要区别之一。

## 5. 工具设计
需要思考：
- Agent 需要哪些工具
- 每个工具的输入输出是否清晰
- 工具失败时怎么办
- 工具是否可组合
- 哪些能力应该做成工具，哪些不该

很多 Agent 项目的核心，其实不在模型，而在工具系统设计。

## 6. 路由与任务拆分
不是所有输入都应该直接进入同一个 Agent 流程。

需要考虑：
- 是否需要前置分类
- 是否区分新建、修改、查询、闲聊
- 是否需要澄清层
- 何时应该拒绝，何时应该继续

这决定了系统是否稳定、可控。

## 7. 持久化
只要系统涉及文件、笔记、任务、记忆，就要考虑：
- 数据存哪里
- 元数据怎么存
- 如何更新
- 如何删除
- 如何做版本管理
- 如何与检索索引保持一致

## 8. RAG / 知识库
只要项目涉及“基于已有资料问答”，就要考虑：
- 数据如何入库
- 如何切块
- 如何检索
- 是否需要 rerank
- 如何返回引用
- 如何增量更新

RAG 不是一个点功能，而是一整条链路。

## 9. 可解释性与引用
需要考虑：
- 系统回答来自哪里
- 哪些是原文，哪些是推断
- 是否能给出引用
- 用户如何验证结果

这会直接影响可信度。

## 10. 错误处理与鲁棒性
Agent 系统比普通应用更容易失败，因为链路更长、依赖更多。

要提前考虑：
- 模型失败怎么办
- 工具失败怎么办
- 外部服务挂了怎么办
- 用户输入不完整怎么办
- 是否有 fallback

## 11. 评估与测试
需要考虑：
- 怎么判断 Agent 做得好不好
- 路由是否正确
- 工具调用是否稳定
- 多轮流程是否会跑偏
- RAG 是否真的检索到了正确内容

没有评估，Agent 很容易“看起来能用，实际上不稳”。

## 12. 前端与交互设计
如果是面向用户的 Agent，不能只看后端。

需要考虑：
- 用户如何知道系统当前在做什么
- 多轮任务如何展示
- 编辑和问答如何区分
- 是否需要任务状态、来源、历史版本展示

## 13. 安全与约束
要思考：
- 工具权限是否过大
- 是否允许任意读写文件
- 输入是否需要过滤
- 是否存在 prompt injection 风险
- RAG 内容是否可信

## 14. 成本与性能
需要考虑：
- token 成本
- 工具调用次数
- 响应延迟
- 检索速度
- 长任务的资源消耗

Agent 的能力越强，越要关注成本控制。

## 15. 可扩展性
最后要问自己：
- 以后要不要支持更多任务
- 以后要不要支持更多工具
- 以后要不要拆成多个子 Agent
- 当前架构是否容易扩展

## 一句话提醒

开发 Agent 时，不要只盯着“模型能不能回答”，还要同时考虑：
- 产品边界
- 状态
- 记忆
- 上下文
- 工具
- 路由
- 持久化
- RAG
- 引用
- 鲁棒性
- 测试
- 前端交互
- 安全
- 成本
- 可扩展性

如果这些方向里有某一项你暂时还没做，不一定是问题；真正的问题是你完全没意识到它会影响整个系统设计。
