# Note Agent 会话状态与笔记状态设计

本文档用于明确两件事：
- `mode` 应该如何设计
- `session state` 与 `note state` 的正式字段边界

目标是让后续“多轮记笔记 / 修改笔记 / 基于笔记问答”不再依赖大量隐式推断，而是建立清晰的状态结构。

## 一、什么是 `mode`

`mode` 表示：

> 当前这个会话，系统正在以什么工作模式服务用户。

它属于 **会话状态**，不属于笔记状态。

### 为什么需要 `mode`

在多轮对话里，用户经常会说一些省略上下文的话，例如：
- “详细一点”
- “改成中文”
- “继续改”
- “那就保存吧”

如果没有 `mode`，系统只能反复从聊天历史中猜测用户当前到底是在：
- 创建新笔记
- 修改已有笔记
- 还是围绕已有笔记做问答

引入 `mode` 后，系统可以更稳定地解释短句和 follow-up 请求。

## 二、推荐的 `mode` 枚举

当前项目建议先使用下面这组最小枚举：

### 1. `create`
表示当前会话正在围绕新的原始资料创建笔记。

典型场景：
- 用户刚贴了一篇文章
- 用户上传了文件
- 用户要求“帮我整理成笔记”

### 2. `edit`
表示当前会话正在修改某篇已有笔记。

典型场景：
- “把刚才那篇改详细一点”
- “重写第二部分”
- “翻译成中文”
- “改成提纲版”

### 3. `qa`
表示当前会话正在围绕某篇已有笔记进行问答，而不是修改正文。

典型场景：
- “这篇笔记主要讲了什么？”
- “它和 ReAct 有什么关系？”
- “根据这篇笔记回答一下……”

### 4. `idle`
表示当前会话暂时没有明确进入某种工作模式。

典型场景：
- 新建空会话
- 用户只是寒暄
- 系统暂时无法判断下一步动作

## 三、`mode` 的推荐切换规则

### 进入 `create`
当满足以下条件之一时：
- 用户提供新的 URL / 文本 / 文件路径
- dispatcher 判定当前任务是新建笔记

### 进入 `edit`
当满足以下条件之一时：
- 用户明确要求修改已有笔记
- 用户引用“刚才那篇 / 这篇 / 上一版”并提出编辑要求
- 当前已有 `active_note_id`，且请求语义明显属于改写、重写、压缩、扩写、翻译、润色

### 进入 `qa`
当满足以下条件之一时：
- 用户围绕已有笔记提问
- 用户没有要求改正文，而是在问内容、概念、总结、差异、解释

### 回到 `idle`
当满足以下条件之一时：
- 用户新开线程
- 当前任务结束且没有明确后续模式
- 用户输入与笔记系统无关

## 四、什么是会话状态（Session State）

会话状态回答的是：

> 当前这个 thread / session 现在正在发生什么？

它应当按 `thread_id` 持久化。

### 会话状态的正式字段表

| 字段名 | 类型 | 是否推荐当前实现 | 说明 |
| --- | --- | --- | --- |
| `thread_id` | `str` | 是 | 当前会话唯一标识 |
| `messages` | `list[BaseMessage]` | 是 | 当前会话消息历史 |
| `active_note_id` | `str \| None` | 是 | 当前会话正在处理的笔记 |
| `active_note_title` | `str \| None` | 是 | 当前活动笔记标题 |
| `mode` | `Literal["idle", "create", "edit", "qa"]` | 建议下一步实现 | 当前会话工作模式 |
| `intent` | `str \| None` | 是 | 当前轮 dispatcher 输出意图 |
| `session_messages` | `list[BaseMessage] \| None` | 是 | 已恢复的持久化消息历史 |
| `last_user_goal` | `str \| None` | 建议后续实现 | 用户最近明确的目标摘要 |
| `working_note_constraints` | `dict \| None` | 建议后续实现 | 当前笔记的风格要求，如“详细/提纲/中文” |
| `updated_at` | `str \| None` | 可放到 session 文件里 | 该会话最近更新时间 |

## 五、什么是笔记状态（Note State）

笔记状态回答的是：

> 这篇笔记本身是什么？

它应当按 `note_id` 持久化。

### 笔记状态的正式字段表

| 字段名 | 类型 | 是否推荐当前实现 | 说明 |
| --- | --- | --- | --- |
| `note_id` | `str` | 是 | 笔记唯一标识 |
| `title` | `str` | 是 | 笔记标题 |
| `filename` | `str` | 是 | Markdown 文件名 |
| `content` | `str` | 是 | 笔记正文内容 |
| `summary` | `str` | 是 | 简短摘要 |
| `tags` | `list[str]` | 是 | 标签 |
| `source_type` | `str` | 是 | 来源类型，例如 `url / text / file_path / mixed` |
| `source_ref` | `str` | 是 | 主来源引用 |
| `source_refs` | `list` | 可选 | 多来源引用 |
| `thread_id` | `str \| None` | 建议保留 | 首次创建该笔记的会话来源 |
| `status` | `str` | 是 | 如 `active / archived` |
| `version` | `int` | 是 | 当前版本号 |
| `created_at` | `str` | 是 | 创建时间 |
| `updated_at` | `str` | 是 | 最近修改时间 |
| `last_modified_from` | `str` | 是 | 最近修改来源，如 `create / edit / rewrite / rag_update` |
| `rag_indexed` | `bool` | 是 | 是否已完成向量化索引 |

## 六、为什么必须拆开

因为会话状态和笔记状态不是一个维度。

### 会话状态表达的是：
- 当前正在编辑哪篇笔记
- 当前在创建 / 编辑 / 问答哪种模式
- 最近用户要求了什么
- 当前对话上下文是什么

### 笔记状态表达的是：
- 这篇笔记标题是什么
- 内容是什么
- 第几版
- 来源是什么
- 是否做过 RAG 索引

如果不拆开，会出现这些问题：
- 一个会话切换多篇笔记时状态混乱
- 多个会话同时访问同一篇笔记时边界不清
- `active_note_id` 这类会话字段被误当成笔记本身属性
- 后续做 RAG、记忆、版本管理会越来越难扩展

## 七、当前项目的推荐实现顺序

### 第一步
在 `AgentState` 中正式加入：
- `mode`
- 后续视需要加入 `last_user_goal`
- `working_note_constraints`

### 第二步
在 session persistence 中保存：
- `messages`
- `active_note_id`
- `active_note_title`
- `mode`
- 后续的短期记忆字段

### 第三步
保持 note store 只管理：
- 笔记正文
- 笔记元数据
- 版本与索引

不要让 note store 直接承担当前会话模式。

## 八、一句话总结

- `session state` 回答的是“这个会话现在在做什么”
- `note state` 回答的是“这篇笔记本身是什么”
- `mode` 是会话状态里的关键字段，用于明确当前会话是在 `create`、`edit`、`qa` 还是 `idle`
