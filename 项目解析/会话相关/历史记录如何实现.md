# 历史记录如何实现

本文档说明当前版本 `note_agent` 中“历史记录”是如何实现的，包括：

- 历史记录保存的是什么
- 它和短期记忆的关系
- 当前存在哪里
- 后端如何写入
- 前端如何读取和展示

## 1. 什么是历史记录

在这个项目里，历史记录主要指的是：

> 某个 thread 的会话历史展示数据。

它不是笔记正文，也不是长期记忆，而是：

- thread 的消息历史摘要
- 当前活动笔记信息
- 最近模式与更新时间

也就是说，历史记录更接近：

> thread 短期记忆的一层前端展示投影。

## 2. 历史记录和短期记忆的关系

这点很重要。

### 短期记忆关注的是

- 当前 thread 怎么继续工作
- 下一轮应该接什么上下文
- 当前活动笔记是谁
- 当前 mode / operation 是什么

### 历史记录关注的是

- 前端要如何展示这个 thread
- 历史列表里显示什么 preview
- 点开 thread 后要把哪些消息先展示出来

所以：

- 历史记录不是独立记忆系统
- 它是 thread 短期记忆的一层 projection / read model

## 3. 当前历史记录不再保存在哪里

旧版本曾经使用：

- `backend/data/sessions/<thread_id>.json`

来保存会话历史。

但当前实现已经不再以 JSON 文件作为历史记录主实现。

也就是说：

- 当前项目已经去除了 JSON sessions 文件作为历史主来源
- 旧文档里涉及 `backend/data/sessions/` 的描述都已过时

## 4. 当前历史记录保存在哪里

当前历史记录保存在 PostgreSQL 中的一张 projection 表里：

- `session_history_projection`

这张表由后端主动维护，用于：

- 前端历史列表
- 前端历史详情
- thread 预览展示

它不是 LangGraph 短期记忆的 source of truth，而是：

> 专门为前端查询准备的一张派生表。

## 5. 当前历史记录里保存了什么

当前 projection 表至少保存这些字段：

- `thread_id`
- `updated_at`
- `preview`
- `intent`
- `mode`
- `operation`
- `active_note_id`
- `active_note_title`
- `messages`

其中最重要的是：

### 5.1 `thread_id`

表示这条历史记录属于哪个 thread。

### 5.2 `updated_at`

表示这个 thread 最近一次被更新的时间。

前端历史列表通常会按它排序。

### 5.3 `preview`

表示 thread 的简短预览文本。

当前实现里，它通常取第一条人类消息的主要文本内容。

### 5.4 `mode`

表示当前 thread 最近一次处于什么工作模式。

例如：

- `idle`
- `create`
- `edit`
- `qa`

### 5.5 `active_note_id`

表示这个 thread 当前活动笔记是谁。

### 5.6 `active_note_title`

表示这个 thread 当前活动笔记的用户可读标题。

### 5.7 `messages`

表示这个 thread 的消息历史投影。

这不是 LangGraph 内部完整持久化结构本身，而是：

> 面向前端读取和展示做过归一化后的消息数据。

## 6. 后端如何写入历史记录

后端写入历史记录的核心模块在：

- `backend/src/agent/session_store.py`

当前做法是：

1. 主图每轮执行结束后进入 `export_session`
2. `export_session` 调用 `export_session_snapshot`
3. 把当前 thread 的关键字段 upsert 到 PostgreSQL projection 表

也就是说：

- 每轮图执行都会刷新历史 projection
- 历史记录始终和最新 thread 状态同步

## 7. 后端和真实短期记忆的边界

这也是当前架构里最重要的边界之一。

### LangGraph persistence 负责

- thread 的真实短期记忆
- 下一轮运行要继续使用的上下文

### session history projection 负责

- 给前端列表和详情页提供稳定读模型
- 把 thread 状态压平成更容易查询的结构

所以不能把 projection 表理解成“真正的会话 source of truth”。

更准确地说：

- 短期记忆主来源：LangGraph persistence
- 历史记录展示来源：PostgreSQL projection 表

## 8. 前端如何读取历史记录

前端现在不是直接去扫本地目录，而是通过服务端 API 查 PostgreSQL。

### 8.1 列表接口

文件：

- `frontend/src/app/api/session-history/route.ts`

作用：

- 读取所有 thread 历史概览
- 返回 preview、更新时间、mode、active note 等信息

### 8.2 详情接口

文件：

- `frontend/src/app/api/session-history/[threadId]/route.ts`

作用：

- 根据 `threadId` 读取对应历史详情
- 返回该 thread 的 messages 和相关状态

### 8.3 PostgreSQL 读取层

文件：

- `frontend/src/lib/session-history-store.ts`

作用：

- 统一连接 PostgreSQL
- 查询 `session_history_projection`
- 把表结构转换为前端能直接用的 thread history 数据

## 9. 前端如何展示历史记录

前端历史展示主要涉及：

- `frontend/src/providers/Thread.tsx`
- `frontend/src/components/thread/history/index.tsx`

当前思路是：

1. 先从 `session-history` API 拿本地可展示的 thread 历史
2. 再把它和 LangGraph remote threads 做 merge
3. 统一展示在历史侧栏里

这样做的好处是：

- 历史列表有稳定展示来源
- 不完全依赖某一次运行时返回的数据
- 更适合你当前“会话状态 + 展示投影”这种架构

## 10. 为什么需要 projection 表

如果直接让前端去读 LangGraph 持久化的底层结构，会有几个问题：

- 查询结构不够前端友好
- 不容易直接拿到展示所需字段
- 列表页通常只关心摘要，不关心完整底层存储格式

所以当前项目用了一张 projection 表，专门服务：

- 历史列表
- 历史详情
- 预览展示

这就是 projection 的意义：

> 从真实状态里提炼出更适合查询和展示的一层结构。

## 11. 当前历史记录实现的价值

现在这套历史记录实现至少带来了这些能力：

- 历史展示不再依赖 JSON 文件
- 前后端都围绕 PostgreSQL 查询
- 历史记录和 thread 状态边界更清晰
- 会话展示层更接近标准数据库读模型

## 12. 当前还可以继续增强的方向

后续如果继续优化，比较值得做的是：

- 增加更好的 `preview` 生成策略
- 增加 thread 标题生成策略
- 增加 projection 层的一致性测试
- 处理 projection 异常时的降级策略

如果想继续顺着代码看，主要关注这些位置即可：

### 后端

## 14. 一句话总结

在当前版本的 `note_agent` 中，历史记录已经不再通过本地 JSON 文件实现，而是：

> 以 PostgreSQL `session_history_projection` 表作为前端历史展示的读模型，由后端每轮导出、前端通过 API 查询并展示。
