# 历史记录如何实现

本文档说明 `note_agent` 项目中的“历史记录”是如何实现的，包括：
- 历史记录保存的是什么
- 历史记录保存在哪里
- 后端如何写入和恢复历史记录
- 前端如何把历史记录展示出来

## 1. 什么是历史记录

在这个项目里，历史记录主要指的是：

> 某个会话（thread）里已经发生过的消息历史和相关上下文。

它不是笔记正文，也不是长期记忆，而是一个 thread 的对话历史。

在当前项目里，历史记录主要包括：
- 用户消息
- AI 消息
- 当前活动笔记相关状态
- 最近一次意图等辅助信息

## 2. 历史记录和笔记正文不是一回事

这点很重要。

### 历史记录保存的是
- 对话过程
- 这个会话之前说过什么
- 当前会话最近在处理哪篇笔记

### 笔记正文保存的是
- 最终产出的 Markdown 内容
- 被持续编辑的笔记对象本身

所以：
- 历史记录属于会话层
- 笔记正文属于笔记对象层

## 3. 历史记录保存在哪里

当前项目已经实现了本地会话持久化。

每个会话对应一个文件：
- `backend/data/sessions/<thread_id>.json`

也就是说：
- 一个 thread 对应一份会话历史文件
- 文件名就是 thread 的标识
- 这样同一个 thread 再次进入时，就能恢复原来的上下文

## 4. 历史记录里保存了什么

当前项目里，一份 session 文件主要会保存这些内容：
- `thread_id`
- `messages`
- `active_note_id`
- `active_note_title`
- `intent`
- `updated_at`

其中最重要的是 `messages`。

### 4.1 `messages`
这里保存的是当前会话的消息历史。

它包括：
- 用户消息
- AI 消息
- 可能还有工具相关消息

这些消息会被序列化后写入本地 JSON 文件。

### 4.2 `active_note_id`
表示当前这个会话正在围绕哪篇笔记工作。

它很重要，因为很多 follow-up 表达依赖这个字段，例如：
- “把刚才那篇改详细一点”
- “把这篇压缩一下”
- “把上一版翻成中文”

### 4.3 `active_note_title`
表示当前活动笔记的标题。

它更多用于：
- 上下文提示
- 前端展示
- 调试和日志

### 4.4 `intent`
表示最近一轮 dispatcher 处理得到的意图。

### 4.5 `updated_at`
表示这份历史记录最近一次更新时间。

这个字段对前端很有用，因为历史列表通常会按最近更新时间排序。

## 5. 后端如何保存历史记录

后端保存历史记录的核心思想是：

> 每次一轮图执行结束后，把当前 thread 的状态写回本地 session 文件。

### 5.1 保存入口
当前项目专门有一个会话持久化模块：
- `backend/src/agent/session_store.py`

这里负责：
- 把消息历史写入本地
- 把当前活动笔记信息写入本地
- 把 thread 级状态组织成 JSON 文件

### 5.2 图中的保存流程
在主图中，当前项目加入了专门的保存节点：
- `save_session`

主图大致流程是：
- `restore_session`
- `dispatch`
- `react_agent`（如需要）
- `save_session`
- `END`

这意味着：
- 无论本轮是普通等待、退出，还是实际进入 ReAct Agent
- 最终都会走到保存会话这一步

### 5.3 为什么不是每次只保留内存
如果只保留内存，那么：
- 服务重启后会话就丢失
- 前端也无法恢复 thread 历史

所以当前项目把历史记录正式写入本地磁盘。

## 6. 后端如何恢复历史记录

历史记录的恢复逻辑和保存逻辑是配对的。

### 6.1 恢复入口
在图开始执行前，主图会先进入：
- `restore_session`

它会根据 `thread_id` 去找：
- `backend/data/sessions/<thread_id>.json`

如果存在：
- 读取这份会话历史
- 恢复消息历史
- 恢复当前活动笔记信息

如果不存在：
- 说明这是新会话
- 就按空状态处理

### 6.2 为什么需要 `session_messages`
当前项目实现时，还专门加了一个：
- `session_messages`

它的作用是：
- 区分“从本地恢复出来的旧历史”
- 和“当前这一轮刚刚输入的新消息”

这样做是为了避免 `MessagesState` 的追加机制把历史消息重复叠加。

这是一个偏实现层的字段，但对正确恢复历史非常重要。

## 7. 前端如何展示历史记录

当前项目前端的历史展示不是单靠 LangGraph 线程内存，而是专门补了一层“本地 session 历史展示”。

### 7.1 历史列表 API
前端新增了一个列表接口：
- `frontend/src/app/api/session-history/route.ts`

它会读取：
- `backend/data/sessions/`

然后返回：
- 所有持久化 session 的概览
- 以及每个 thread 的 preview、更新时间等信息

### 7.2 历史详情 API
前端还新增了一个详情接口：
- `frontend/src/app/api/session-history/[threadId]/route.ts`

它的作用是：
- 根据 threadId 读取对应 session 文件
- 把消息历史返回给前端

### 7.3 历史侧栏
前端历史侧栏在：
- `frontend/src/components/thread/history/index.tsx`

它会展示：
- 持久化 thread 列表
- 每个 thread 的标题预览

### 7.4 主聊天界面里的历史回显
前端主聊天界面在：
- `frontend/src/components/thread/index.tsx`

这里做了两件重要的事：
1. 当用户点击某个已有 thread 时，会去请求该 thread 的持久化历史
2. 如果当前流式状态里还没有历史消息，就先显示持久化历史

这样即使：
- 后端服务刚重启
- LangGraph 运行时内存里的 thread 已丢失

前端仍然可以把这个 thread 的历史内容先显示出来。

## 8. 为什么要单独做前端历史展示补层

如果只依赖运行时 thread 状态，会有一个问题：
- 服务一旦重启
- 运行时内存里的 thread 历史就可能拿不到
- 用户前端看到的聊天界面会像“空白”一样

所以当前项目加了一层：
- 从本地 session 文件直接读取历史
- 让前端先把它显示出来

这使得“重启后还能看到历史”成为可能。

## 9. 历史记录是如何支撑多轮对话的

历史记录不是为了“备份聊天内容好看”，它的真正作用是支撑多轮语境。

例如：
- 用户上一轮刚生成了一篇笔记
- 当前活动笔记已经保存到 session
- 下一轮用户说：“把刚才那篇改详细一点”

系统之所以能理解这句话，依赖的是：
- 历史消息恢复
- 当前活动笔记恢复
- 会话状态恢复

所以历史记录的意义不只是“看得见历史”，还包括：

> 让系统可以继续沿用之前的上下文工作。

## 10. 当前历史记录实现的价值

当前项目的历史记录实现，至少带来了这些能力：
- 会话可以本地持久化
- 服务重启后，thread 可以恢复上下文
- 前端历史侧栏可以列出已保存的 session
- 点击 thread 后，前端可以先展示持久化历史
- 多轮编辑“刚才那篇笔记”这类操作更稳定

## 12. 一句话总结

在 `note_agent` 中，历史记录的实现本质上是：

> 以 `thread_id` 为单位，把会话消息和活动笔记等上下文写入本地 `sessions` 目录，并通过前后端配合，在后端重启后仍然能够恢复和展示这些历史记录。
