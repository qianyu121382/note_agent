# 会话状态如何管理

本文档说明 `note_agent` 当前版本中的会话状态是什么、为什么需要它、它和笔记状态有什么区别，以及现在系统是如何管理这套状态的。

## 1. 什么是会话状态

会话状态（session state / thread state）指的是：

> 当前这个对话线程正在做什么，以及下一轮应该如何继续。

它不是某篇笔记本身的内容，而是 thread 级上下文。

例如：

- 当前 thread 里已经说过哪些话
- 当前正在处理哪篇笔记
- 当前是在创建、编辑还是围绕已有笔记问答
- 当前有没有等待用户补充的信息

这些都属于会话状态。

## 2. 为什么需要会话状态

如果没有会话状态，多轮对话就会退化成一轮一轮的孤立请求。

例如：

1. 用户先让系统整理一篇资料
2. 系统生成了一篇笔记
3. 用户接着说：`把刚才那篇改详细一点`

如果系统没有会话状态，它就很难知道：

- “刚才那篇”指的是哪篇笔记
- 当前是在继续编辑，而不是重新新建一篇
- 当前 thread 的工作目标是什么

所以会话状态的作用就是：

> 让系统在同一个 thread 中，持续记住当前语境，并把下一轮输入接回正确任务。

## 3. 会话状态和笔记状态的区别

这两个概念很容易混，但本质上属于两层不同对象。

### 会话状态回答的是

- 当前这个 thread 正在做什么
- 当前正在围绕哪篇笔记继续工作
- 当前这一轮的任务类型是什么
- 下一轮输入应该接回哪个上下文

### 笔记状态回答的是

- 这篇笔记本身是什么
- 标题、正文、来源、版本分别是什么
- 这篇笔记当前处于什么业务状态

所以：

- `active_note_id` 属于会话状态
- `note_id` 属于笔记状态
- `messages` 属于会话状态
- `title / version / source_ref` 属于笔记状态

## 4. 当前项目中的会话状态字段

当前主状态定义在：

- `backend/src/agent/state.py`

现在项目已经采用 `MessagesState` 风格，把 `messages` 作为主状态，再叠加少量结构化字段。

### 4.1 `messages`

这是当前 thread 的消息历史。

作用：

- 保留用户和 AI 的上下文
- 支撑多轮 follow-up
- 给 ReAct agent 构造历史上下文

### 4.2 `intent`

表示当前这一轮 dispatcher 的顶层判断结果。

常见值：

- `note_taking`
- `waiting`
- `exit`

### 4.3 `mode`

表示当前 thread 处于哪种工作模式。

当前最主要的模式：

- `idle`
- `create`
- `edit`
- `qa`

它的作用是：

- 让系统知道当前是在新建笔记、修改笔记，还是围绕已有笔记问答

### 4.4 `operation`

表示更细粒度的当前操作。

例如：

- `create_note`
- `locate_note`
- `expand_note`
- `translate_note`
- `summarize_note`
- `general_follow_up`

这让系统不只知道“在 edit”，还知道“这次 edit 更像扩写还是翻译”。

### 4.5 `active_note_id`

表示当前 thread 正在围绕哪篇笔记工作。

这个字段很关键，因为很多 follow-up 输入都是省略表达，例如：

- `继续改一下`
- `翻译成中文`
- `把这篇压缩一下`

系统之所以能理解这些表达，依赖的就是当前会话里的 `active_note_id`。

### 4.6 `active_note_title`

表示当前活动笔记的可读标题。

作用主要是：

- 上下文提示
- 历史列表展示
- 日志与调试输出

### 4.7 `pending_clarification`

表示当前 thread 是否处于“等待用户补信息”的状态。

当前最小实现已经支持：

- `none`
- `note_target`
- `edit_operation`

这意味着系统已经开始支持“澄清回复”机制。

### 4.8 `pending_question`

表示上一轮 agent 向用户提出的澄清问题。

例如：

- `你想处理哪一篇笔记？`
- `你想对这篇笔记做什么操作？`

### 4.9 `pending_context`

表示这次澄清属于哪个原始任务。

它的作用是：

- 让下一轮用户的简短回答，被解释成“补全上一轮任务”
- 而不是被当成一个全新请求

## 5. 当前项目中会话状态如何流转

当前主图在：

- `backend/src/agent/graph.py`

真实流程是：

`dispatch -> react_agent -> export_session`

### 第一步：dispatch

当前轮用户输入进入后，dispatcher 会做这些事：

- 提取用户输入
- 判断顶层 `intent`
- 推断 `mode`
- 推断 `operation`
- 必要时触发澄清状态

也就是说，dispatcher 不再只是“能不能进入主链”，而是在做 thread-aware 路由。

### 第二步：react_agent

如果本轮确实需要进入笔记主链，就进入 ReAct agent。

此时会结合：

- 当前用户输入
- 历史消息
- 当前活动笔记
- 当前 `mode / operation`

来决定：

- 是创建新笔记
- 还是定位已有笔记
- 还是更新已有笔记
- 还是基于已有笔记问答

### 第三步：export_session

本轮结束后，会把 thread 状态导出到历史展示层。

注意：

- 这一步不再是“把会话当 source of truth 持久化到本地 JSON”
- 当前系统中，短期记忆主来源是 LangGraph persistence
- `export_session` 负责的是把当前 thread 状态写入 PostgreSQL projection 表，供前端历史展示查询

## 6. 会话状态是如何持久化的

当前项目已经不再依赖旧的本地 `sessions/*.json` 文件作为主会话存储。

现在更准确的结构是：

### 6.1 线程短期记忆

由 LangGraph 标准持久化负责。

这层保存的是：

- thread 级 messages
- thread 级 state
- 用于下一轮继续运行的真实上下文

### 6.2 历史展示投影

由：

- `backend/src/agent/session_store.py`

负责把当前 thread 状态写入 PostgreSQL 的 `session_history_projection` 表。

这层不是短期记忆 source of truth，而是：

> 面向前端历史列表与历史详情查询的读模型。

## 7. 当前项目中的澄清回复机制

这是当前会话状态里一个新加入的重要点。

当用户输入不够明确时，系统不会盲目继续执行，而是先进入澄清状态。

例如：

- 用户：`帮我改一下这篇`
- 系统：`你想处理哪一篇笔记？`
- 用户：`RAG 那篇`

这里第二轮用户输入“RAG 那篇”不是一个完整新请求，而是对上一轮问题的回答。

当前系统就是通过：

- `pending_clarification`
- `pending_question`
- `pending_context`

来管理这种未完成状态。

这使得系统能够区分：

- 普通 follow-up
- 澄清回复

## 8. 当前会话状态的价值

现在这套会话状态至少已经支撑了这些能力：

- 同一 thread 中持续多轮工作
- 围绕 `active_note` 继续编辑或问答
- 基于 `mode / operation` 判断当前动作
- 对不完整请求先追问而不是误处理
- 历史记录可以稳定展示给前端

## 9. 当前还可以继续增强的方向

虽然当前会话状态已经成型，但还可以继续补强，例如：

- 更细粒度的澄清类型
- 更强的 thread 内目标摘要
- 更稳定的目标笔记切换判断
- 对连续多轮 follow-up 的测试覆盖

## 11. 一句话总结

在当前 `note_agent` 中，会话状态就是“某个 thread 当前的工作上下文”。

它已经不只是消息历史，而是一套围绕：

- `messages`
- `mode`
- `operation`
- `active_note`
- `pending_clarification`

组织起来的线程级短期记忆系统。
