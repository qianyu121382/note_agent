# 会话状态如何管理

本文档说明 `note_agent` 项目中的“会话状态”是什么、为什么需要它、它和笔记状态的区别，以及当前项目是如何管理会话状态的。

## 1. 什么是会话状态

会话状态（Session State）指的是：

> 当前这个对话线程（thread / session）正在发生什么。

它描述的是“这个会话此刻的上下文”，而不是某篇笔记本身的结构。

例如：
- 当前这个会话的历史消息有哪些
- 当前这个会话正在处理哪篇笔记
- 当前用户这一轮是在创建笔记、修改笔记，还是在围绕已有笔记问答
- 当前会话最近一次处理到了哪里

这些都属于会话状态。

## 2. 为什么需要会话状态

如果没有会话状态，多轮对话就会很脆弱。

举个例子：
- 用户先让系统整理一篇文章
- 系统生成并保存了一篇笔记
- 用户接着说：“把刚才那篇改详细一点”

如果系统没有会话状态，它就很难知道：
- “刚才那篇”指的是哪篇笔记
- 当前用户是在继续编辑上一轮结果，而不是重新新建一篇笔记
- 当前对话到底承接的是哪条上下文

所以会话状态的作用就是：

> 让系统能在同一个 thread 中，持续记住“当前对话上下文”。

## 3. 会话状态和笔记状态的区别

这两个概念很容易混淆，但实际上它们负责的是两类完全不同的问题。

### 会话状态回答的是
- 当前这个会话正在做什么
- 当前这个 thread 里正在操作哪篇笔记
- 最近的上下文是什么
- 用户刚才那句省略表达该如何解释

### 笔记状态回答的是
- 这篇笔记本身是什么
- 标题是什么
- 内容是什么
- 来源是什么
- 版本是多少

所以：
- `active_note_id` 属于会话状态
- `note_id` 属于笔记状态
- `messages` 属于会话状态
- `title / version / source_ref` 属于笔记状态

## 4. 当前项目中的会话状态管理思路

当前项目已经开始把会话当成一个正式对象来管理。

它的核心思路是：
- 每个会话由 `thread_id` 标识
- 同一个 `thread_id` 的上下文会被恢复
- 每一轮处理结束后，会把新的上下文写回本地

也就是说：
- 多轮对话不是靠“图一直活着”实现的
- 而是靠“同一个 thread 的状态不断恢复和保存”实现的

## 5. 当前项目中的会话状态包含什么

### 5.1 消息历史 `messages`
这是最核心的会话状态之一。

它表示：
- 这个会话里，用户和系统之前说过什么

这些历史消息会影响：
- 当前这一轮用户输入的理解
- ReAct agent 的上下文构造
- 多轮 follow-up 请求的解释

### 5.2 当前活动笔记 `active_note_id`
它表示：
- 这个会话当前正在围绕哪篇笔记工作

这很重要，因为很多 follow-up 输入都是省略式的，例如：
- “继续改一下”
- “翻译成中文”
- “把这篇压缩一下”

系统之所以能理解这些话，依赖的就是当前会话里保存的 `active_note_id`。

### 5.3 当前活动笔记标题 `active_note_title`
它表示：
- 当前活动笔记的用户可读标题

作用主要是：
- 便于上下文提示
- 便于后续 UI 展示
- 便于日志和解释性输出

### 5.4 当前意图 `intent`
它表示：
- 这一轮 dispatcher 判断出来的任务意图

例如：
- `note_taking`
- `waiting`
- `exit`

这个字段更多是本轮调度结果，但也会被保存到 session 中，帮助恢复最近一次运行状态。

### 5.5 已恢复的持久化消息 `session_messages`
这个字段的作用是：
- 区分“从本地恢复出来的旧消息”
- 和“当前这轮刚进来的新消息”

它的存在是为了避免 `MessagesState` 的消息追加机制把历史消息重复叠加。

换句话说，这个字段更偏工程实现层，不是用户可感知状态，但对系统正确恢复多轮会话非常重要。

## 6. 当前项目中会话状态是如何流转的

当前项目的主图结构大致可以理解为：

`恢复会话 -> 调度 -> 必要时进入 ReAct Agent -> 保存会话`

### 第一步：恢复会话
当新的请求进入后，系统会先尝试根据 `thread_id` 找到对应的本地 session 文件。

如果找到了：
- 加载历史消息
- 加载 `active_note_id`
- 加载 `active_note_title`

如果没找到：
- 说明这是一个新会话
- 就从空状态开始

### 第二步：调度当前输入
恢复状态之后，系统再处理当前这一轮的新输入。

这时 dispatcher 会综合考虑：
- 当前用户这句话是什么
- 当前会话是不是已经有活动笔记

例如：
- 如果当前已有 `active_note_id`
- 且用户说的是“把刚才那篇改详细一点”

那么系统会把它理解为一次继续编辑，而不是全新任务。

### 第三步：运行主任务
如果需要进入主处理链，就会进入 ReAct Agent。

ReAct Agent 在执行时，会接收到：
- 当前轮用户的新输入
- 恢复出来的历史会话消息
- 当前活动笔记信息

然后它再决定：
- 是读取某篇已有笔记
- 还是处理新的资料
- 是创建新笔记
- 还是更新已有笔记

### 第四步：保存会话
本轮完成之后，系统会把更新后的会话状态再写回本地。

这一步通常会保存：
- 最新消息历史
- 最新 `active_note_id`
- 最新 `active_note_title`
- 当前意图
- 更新时间

这样下一轮进来时，就可以接着恢复。

## 7. 会话状态是如何持久化的

当前项目已经实现了本地 session 持久化。

每个会话会保存成一个文件：
- `backend/data/sessions/<thread_id>.json`

这个文件保存的是：
- 该 thread 的消息历史
- 当前活动笔记
- 当前意图
- 更新时间

这意味着：
- 即使服务重启
- 只要同一个 `thread_id` 再次进入
- 系统就可以把这个会话恢复出来

## 8. 会话状态为什么不是“图一直不结束”

这是一个非常容易误解的点。

很多人会以为多轮对话意味着：
- 图一直跑着
- 用户不断往同一条运行里塞消息

但你这个项目不是这样实现的。

当前项目更准确的实现方式是：
- 图定义只有一份
- 每次用户发新消息，图会重新执行一次
- 执行前先恢复该 thread 的旧状态
- 执行后再把新状态保存回去

所以：
- 每一轮是一次新的图运行
- 但这些运行共享同一个 session 持久化状态

这就是当前项目多轮对话成立的基础。

## 9. 当前会话状态还缺什么

当前项目已经有了会话状态雏形，但还没有完全做完。

例如，后续很适合补的字段包括：
- `mode`
  - 当前会话是在 `create`、`edit`、`qa` 还是 `idle`
- `last_user_goal`
  - 用户最近明确表达的目标摘要
- `working_note_constraints`
  - 当前会话里的笔记风格约束，例如“更详细”“提纲式”“中文”

这些字段会让系统少依赖历史消息反复推断，而是把“当前语境”明确保存下来。

## 10. 当前项目中的相关代码位置

如果你想继续看代码，主要关注这些位置即可：

  - `backend/src/agent/state.py`

  - `backend/src/agent/session_store.py`

- 会话恢复、主图流转、会话保存：

- 前端根据 `thread_id` 提交消息、恢复历史：
  - `frontend/src/providers/Stream.tsx`
  - `frontend/src/components/thread/index.tsx`

## 11. 一句话总结

在 `note_agent` 中，会话状态就是“某个 thread 当前的上下文状态”。

它至少包括：
- 消息历史
- 当前活动笔记
- 当前轮意图

它通过 `thread_id` 与本地持久化文件绑定，使系统能够在同一个会话中持续进行多轮对话，并在服务重启后恢复上下文。
