# 多轮对话是怎么实现的

本文档说明 `note_agent` 项目中的多轮对话是如何实现的，重点解释下面几个问题：
- 多轮对话时，到底是一张图，还是多张图
- 为什么同一个会话可以连续聊下去
- 为什么图每次都会重新运行，但用户仍然感觉是在同一个对话里继续
- 后端的会话恢复和保存，在多轮对话里起了什么作用

## 1. 先说结论

这个项目里的多轮对话，不是“图一直运行不结束”。

更准确地说：

- 图的定义只有一份
- 每次用户发送一轮新消息，都会触发这张图重新执行一次
- 但执行之前，会先恢复这个 thread 之前保存的会话状态
- 执行结束后，又会把新的会话状态保存回去

所以用户感觉是在“同一个对话里继续聊”，本质上是：

> 同一个 `thread_id` 对应的会话状态在不断被恢复、更新、再保存。

## 2. 这个项目里有哪些图

当前项目里，可以把图理解成两层。

### 2.1 外层主图

外层主图负责一轮用户请求的整体流程。

大致流程是：
- 恢复会话状态
- 做输入调度
- 如果需要，进入 ReAct agent 处理
- 保存新的会话状态

也就是说，一轮请求并不是直接进入工具调用，而是先经过会话恢复和路由。

相关代码位置：
- `backend/src/agent/graph.py`

### 2.2 ReAct 子图

当调度器判断当前输入需要进入笔记处理主链时，就会进入 ReAct 子图。

这个子图负责：
- 调用模型
- 判断是否需要调用工具
- 调用工具
- 再次把工具结果交给模型
- 直到模型不再继续调用工具

这部分本质上是一次任务内部的“思考 -> 调工具 -> 再思考”的循环。

相关代码位置：
- `backend/src/agent/react_agent/graph.py`

## 3. 多轮对话不是“一次图运行一直挂着”

这是最容易误解的地方。

很多人在刚接触 LangGraph 时，会以为多轮对话意味着：
- 有一张图启动后就一直不结束
- 用户每次发消息，都继续接在这次运行上

但当前这个项目不是这样实现的。

当前项目更接近下面这种机制：
- 用户发一条消息
- 主图跑完一轮
- 这次运行结束
- 下次用户再发消息时，主图重新跑一轮

所以从运行角度看：
- 每一轮用户输入，对应一次新的图执行
- 图执行会结束
- 下一轮再重新开始

## 4. 那为什么用户感觉是连续对话

因为连续性的来源，不是“图一直没结束”，而是“会话状态被保留了”。

也就是说，系统把“上一次对话留下来的上下文”存到了本地。下次同一个 thread 再进来时，先把这些上下文读回来，再继续处理新的输入。

因此对用户来说：
- 上一轮说过的话还在
- 当前正在编辑的笔记还在
- 刚才那篇、这篇、上一版这些自然表达还能成立

这就是多轮对话真正成立的原因。

## 5. 多轮对话的关键：thread_id

这个项目里，多轮对话是否连续，关键不在于模型本身，而在于 `thread_id`。

可以把它理解为：
- 一个 `thread_id` 就是一条独立会话
- 这条会话有自己对应的历史记录文件
- 只要后续请求继续使用同一个 `thread_id`，系统就能恢复之前的状态

因此：
- 同一个 `thread_id` 会延续上下文
- 不同 `thread_id` 之间的上下文彼此隔离

相关代码位置：
- 前端传递 thread 的逻辑：`frontend/src/providers/Stream.tsx`
- 后端按 thread 恢复会话：`backend/src/agent/session_store.py`

## 6. 一轮请求在后端是怎么流转的

下面用一轮典型请求来说明整个过程。

### 第一步：前端发送消息

用户在前端输入一条消息，例如：
- “把刚才那篇笔记改详细一点”

前端会把这条消息连同当前的 `thread_id` 一起发给后端。

### 第二步：后端先恢复 session

主图开始执行后，不是立刻进入 agent，而是先恢复这个 `thread_id` 对应的会话状态。

系统会从本地读取：
- 之前的消息历史
- 当前活动笔记
- 最近一次意图等信息

这样当前这轮执行，就不是从纯空状态开始。

### 第三步：进入 dispatcher

恢复完会话状态后，系统会判断：
- 这次输入是不是笔记任务
- 是新建笔记，还是基于已有笔记继续修改
- 是否需要进入主处理链

如果当前会话已经有 `active_note_id`，并且用户表达像是在继续编辑，就会直接放行进入主处理链。

### 第四步：进入 ReAct 子图

如果需要处理笔记任务，就会进入 ReAct agent。

这时 agent 不只是看到“当前这一句话”，而是会结合：
- 恢复出来的会话消息
- 当前活动笔记信息
- 本轮新的用户输入

然后决定：
- 是否读取已有笔记
- 是否调用修改工具
- 是否生成或更新笔记

### 第五步：保存新的 session

这轮处理结束后，主图会把更新后的会话状态重新写回本地。

这样下次用户再来时，又可以从新的状态继续。

## 7. 多轮对话和历史记录的关系

多轮对话成立，离不开历史记录，但两者不完全等价。

### 历史记录更偏“发生过什么”
例如：
- 用户说了什么
- AI 回了什么
- 当前活动笔记是什么

### 多轮对话更偏“如何连续工作”
例如：
- 下次还能不能理解“刚才那篇”
- 系统能不能知道当前还在编辑哪篇笔记
- 能不能延续上一轮任务语境

所以可以这样理解：

> 历史记录是多轮对话的重要基础，但多轮对话的关键是“恢复并继续使用这些状态”。

## 8. 为什么当前项目已经属于多轮对话

因为它已经具备了下面几个条件：
- 按 `thread_id` 区分不同会话
- 会话消息会持久化到本地
- 当前活动笔记会持久化到本地
- 同一个 thread 再次进入时，会先恢复这些状态
- 后续请求会在这些状态基础上继续执行

这就意味着：
- 系统不仅能记住之前聊过什么
- 还能围绕同一篇笔记继续工作
- 而不是每一轮都完全从头开始

## 9. 当前项目里的一个重要边界

虽然已经实现了多轮对话，但当前项目的多轮对话仍然主要建立在：
- 消息历史
- 当前活动笔记
- 基本会话字段

它还没有形成更强的短期记忆和长期记忆系统，例如：
- 当前用户偏好的结构化保存
- 工作目标摘要
- 长上下文压缩后的工作记忆
- 长期用户偏好记忆

所以现在这套多轮对话更准确地说，是：

> 已经具备连续会话能力的多轮 Agent，而不是完整记忆系统下的强状态 Agent。

## 10. 可以怎样理解“多轮对话”的技术本质

用一句话总结：

> 这个项目的多轮对话，本质上是“同一张图在同一个 `thread_id` 下被重复执行；每次执行前恢复会话状态，每次执行后再保存会话状态”。

因此，多轮对话不是靠模型自动记住全部上下文，也不是靠图永远不结束，而是靠：
- 会话标识
- 状态恢复
- 状态保存
- 同一主图的重复执行
