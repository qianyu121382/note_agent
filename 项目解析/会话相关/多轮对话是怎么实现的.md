# 多轮对话是怎么实现的

本文档说明当前版本 `note_agent` 中，多轮对话到底是怎么成立的。

重点解释这些问题：

- 多轮对话是不是“图一直不结束”
- 为什么每轮图都重新执行，用户却感觉像在同一个对话里继续
- thread 状态、active note、历史 projection 在这里分别起什么作用

## 1. 先说结论

当前项目里的多轮对话，不是“图一直运行不结束”。

更准确地说：

- 图的定义只有一份
- 每次用户发一条新消息，主图都会重新执行一轮
- 同一个 `thread_id` 下的状态会被 LangGraph persistence 保留
- 每轮结束后，系统再把当前 thread 状态投影到历史展示层

所以用户感觉是在“连续对话”，本质上是：

> 同一个 thread 的状态在被持续读取、更新和继续使用。

## 2. 当前项目有哪些图

可以把当前项目理解成两层图。

### 2.1 外层主图

外层主图负责一轮请求的整体流程。

当前真实流程在：

- `backend/src/agent/graph.py`

流程是：

`dispatch -> react_agent -> export_session`

作用分别是：

- `dispatch`
  - 判断当前输入是什么任务
  - 推断 mode / operation
  - 必要时进入等待澄清状态
- `react_agent`
  - 真正执行笔记处理
- `export_session`
  - 把当前 thread 状态导出到历史 projection

### 2.2 ReAct 子图

当 dispatcher 判断当前轮需要进入笔记处理主链时，就会进入 ReAct 子图。

相关位置：

- `backend/src/agent/react_agent/graph.py`

它负责：

- 调用模型
- 判断是否需要调用工具
- 调用工具
- 再把工具结果交回模型
- 直到任务结束

所以多轮对话不是 ReAct 子图本身在跨轮持续运行，而是：

- 每轮进入一次主图
- 需要时进入一次 ReAct 子图

## 3. 为什么每次重新运行，用户仍然感觉在继续聊

因为连续性不来自“某次运行没结束”，而来自：

- 同一个 `thread_id`
- 同一个 thread 的短期记忆
- 当前活动笔记状态

只要这些状态保留下来，下一轮即使是一次新的图执行，也能接上前面的工作。

## 4. 多轮对话真正依赖的几个核心点

### 4.1 `thread_id`

这是多轮连续性的基础。

可以把它理解为：

- 一个 `thread_id` 对应一条独立会话
- 同一个 `thread_id` 下的状态会连续
- 不同 `thread_id` 之间互不干扰

### 4.2 `messages`

这是 thread 的消息历史。

它让系统知道：

- 之前聊过什么
- 当前这句是不是 follow-up
- 当前用户是不是在延续上一轮任务

### 4.3 `mode`

这让系统知道当前 thread 正在处于什么工作模式。

例如：

- `create`
- `edit`
- `qa`

这使得系统不只是看一条消息，而是带着 thread 的工作模式继续决策。

### 4.4 `operation`

这让系统知道当前更细粒度的任务动作是什么。

例如：

- `locate_note`
- `expand_note`
- `translate_note`
- `summarize_note`

### 4.5 `active_note_id`

这是多轮笔记操作成立的关键。

用户很多输入都是省略表达，例如：

- `继续改一下`
- `翻译成中文`
- `把这篇总结一下`

系统之所以能理解这些表达，依赖的就是当前 thread 里保存的 `active_note_id`。

### 4.6 `pending_clarification`

这是当前新加入的一个重要增强点。

它解决的是：

- 用户输入不完整
- 系统先追问
- 用户下一轮只回一个短答案

例如：

- 用户：`帮我改一下这篇`
- 系统：`你想处理哪一篇笔记？`
- 用户：`RAG 那篇`

这里第二轮的 `RAG 那篇` 不是普通 follow-up，而是澄清回复。

当前系统已经开始通过：

- `pending_clarification`
- `pending_question`
- `pending_context`

来支持这种多轮承接。

## 5. 当前一轮请求是怎么流转的

下面用一轮典型请求说明整个过程。

### 第一步：前端发送消息

前端会把：

- 当前用户消息
- 当前 thread_id

一起发给后端。

### 第二步：进入 dispatcher

dispatcher 会判断：

- 这句话是不是 note task
- 当前是 create / edit / qa 哪种模式
- 是否存在 active note
- 是否需要进入澄清状态

### 第三步：如果需要则进入 ReAct agent

如果本轮确实需要执行笔记任务，就会进入 ReAct。

此时 ReAct 会结合：

- 当前用户输入
- 历史 messages
- 当前活动笔记
- 当前 mode / operation

再决定怎么调用工具。

### 第四步：导出历史 projection

本轮执行结束后，会把当前 thread 的关键状态导出到 PostgreSQL history projection。

这样前端就能展示：

- thread 列表
- preview
- 当前 mode
- 当前 active note

## 6. 多轮对话和历史记录的关系

这两个概念相关，但不是一回事。

### 多轮对话关注的是

- 下一轮能不能继续沿正确上下文工作

### 历史记录关注的是

- 前端怎么把这个 thread 展示出来

所以：

- 多轮对话依赖短期记忆
- 历史记录依赖 projection

projection 让历史可见，但真正让系统“继续聊下去”的仍然是 thread 状态本身。

## 7. 为什么当前项目已经属于真正的多轮 Agent

因为它已经具备这些条件：

- 按 `thread_id` 区分会话
- 使用 `MessagesState` 维护 thread 历史
- 有 `mode / operation / active_note`
- 有最小版澄清回复机制
- 会话状态和笔记状态已经分层
- 历史记录已经变成独立 projection 层

这说明它已经不是普通的“单轮 prompt + 工具”模式，而是：

> 一个具备 thread 级状态流转能力的多轮 Agent。

## 8. 当前还不算什么

虽然现在已经是多轮 Agent，但它还没有到“完整记忆系统”。

当前仍然主要是：

- thread 级短期记忆
- active note 续接
- 最小澄清回复

还没有完整做好的部分包括：

- 更细粒度的澄清类型
- 更强的工作目标摘要
- 长期记忆
- 多轮状态压缩

所以更准确的说法是：

> 当前项目已经具备连续会话能力，但还不是长期记忆驱动的强状态 Agent。

## 10. 一句话总结

当前 `note_agent` 的多轮对话，本质上是：

> 同一张主图在同一个 `thread_id` 下被重复执行；每次执行时使用 thread 短期记忆继续工作，并把当前状态导出为历史展示 projection。
