# 笔记状态如何管理
本文档说明当前版本 `note_agent` 中，笔记对象和笔记元数据如何被管理，以及它和会话状态的边界。

## 1. 笔记状态是什么
笔记状态描述的是“某篇笔记本身是什么”，而不是“当前 thread 正在做什么”。

它关心的内容包括：
- 这篇笔记的唯一标识
- 标题和正文
- 摘要、标签、来源
- 当前版本号
- 最近更新时间
- 是否已经完成 RAG 索引

这些信息属于笔记对象层，不属于会话层。

## 2. 当前实现的主存储
当前项目已经把笔记主存储迁移到 PostgreSQL。

核心代码在：
- `backend/src/agent/tools/note_store.py`

当前真实存储模型是：
- `notes` 表：作为笔记正文和元数据的主存储
- `note_store.py`：封装笔记对象的 CRUD、搜索和版本控制

旧的磁盘目录：
- `backend/data/notes/`
- `backend/data/notes_meta/`
- `backend/data/notes_index.json`

已经不再作为运行时主存储，只用于历史迁移阶段的数据回填。

## 3. 当前笔记对象的核心字段
当前 `note_store.py` 里的核心模型仍然是 `NoteMetadata` 和 `NoteRecord`。

主要字段包括：
- `note_id`
- `title`
- `filename`
- `summary`
- `tags`
- `source_type`
- `source_ref`
- `source_refs`
- `thread_id`
- `status`
- `version`
- `created_at`
- `updated_at`
- `last_modified_from`
- `rag_indexed`

其中：
- `NoteMetadata` 负责结构化元数据
- `NoteRecord` 负责 `metadata + content`

## 4. 为什么正文和元数据一起进数据库
当前实现把正文 `content` 和元数据一起放进 PostgreSQL，原因是：

- 更新可以在同一事务里完成
- 不会出现“元数据更新了但文件没写成功”的分裂状态
- 更适合后续做 RAG chunking 和检索
- 更适合做版本控制和并发保护

这比“正文放 Markdown、元数据放 JSON、索引单独一份”更标准，也更稳。

## 5. 当前已有的底层能力
`backend/src/agent/tools/note_store.py` 当前已经提供这些能力：

### 5.1 `create_note`
- 创建一篇新笔记
- 生成 `note_id`
- 生成 `filename` 作为文件名提示
- 将正文和元数据写入 PostgreSQL

### 5.2 `get_note`
- 根据 `note_id` 读取完整笔记
- 返回 `NoteRecord(metadata, content)`

### 5.3 `update_note`
- 更新正文或标题等元数据
- 自动递增 `version`
- 支持 `expected_version` 做并发保护

### 5.4 `list_notes`
- 按更新时间倒序列出已有笔记

### 5.5 `search_notes`
- 基于 `note_id`、标题、摘要、文件名做轻量搜索

### 5.6 `note_filename_exists`
- 检查某个文件名提示是否已占用

## 6. `filename` 现在的含义
迁移到 PostgreSQL 之后，`filename` 不再表示运行时必须落盘的 Markdown 文件路径。

它现在更像：
- 一个稳定的人类可读文件名提示
- 未来导出 Markdown 时可直接复用的默认文件名
- 搜索和展示时的辅助字段

也就是说，当前运行时的 source of truth 是数据库，而不是磁盘文件。

## 7. 笔记状态和会话状态的边界
这两层现在是明确分开的。

### 笔记状态负责
- 笔记正文
- 笔记元数据
- 版本控制
- 来源信息
- RAG 索引状态

### 会话状态负责
- 当前 thread 的 `messages`
- 当前 `mode`
- 当前 `operation`
- 当前 `active_note_id`
- 当前是否处于 `pending_clarification`

两者的连接点主要是：
- `active_note_id`
- `active_note_title`

thread 只记录“当前在操作哪篇笔记”，真正的笔记本体仍由 `note_store` 管理。

## 8. Agent 如何操作笔记对象
LLM 不直接调数据库，而是通过工具层操作笔记对象。

相关代码：
- `backend/src/agent/tools/local_tools.py`

对外暴露的主要工具有：
- `create_note_record`
- `read_note`
- `update_note_record`
- `list_note_records`
- `search_note_records`
- `check_filename_exists`

这意味着：
- `note_store.py` 管底层笔记对象
- `local_tools.py` 管 Agent 可调用接口

## 9. 这层现在最值得讲的点
从工程角度讲，当前笔记层的亮点是：

- 笔记已经成为正式对象，而不是随手生成的 `.md`
- 正文和元数据已经统一迁入 PostgreSQL
- 已有版本号和并发冲突保护
- 已给 RAG 预留 `rag_indexed` 状态位
- 已能和会话状态通过 `active_note_id` 自然衔接

## 10. 后续最自然的演进方向
这层后续最值得继续做的是：

- 在 PostgreSQL 基础上补 RAG chunk 索引
- 增强搜索能力
- 增加引用与来源追溯
- 把当前 `notes` 表继续扩展成更完整的知识对象层

## 11. 一句话总结
当前版本的 `note_agent` 里，笔记状态已经从“磁盘 Markdown + JSON 索引”升级成了“PostgreSQL 中可读、可写、可检索、可版本化的笔记对象层”。
